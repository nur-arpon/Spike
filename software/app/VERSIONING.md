# Versions

## The one source

`spike_app/pubspec.yaml`: `version: MAJOR.MINOR.PATCH+BUILD` (now `1.0.1+2`). Everything else follows it:

| Where | Value | How |
|---|---|---|
| Settings > About, the app's hello to the brain | `Version 1.0.1` | `lib/core/version.dart`, generated by `dart run tool/sync_brand.dart` (a test checks it matches pubspec) |
| Microsoft Store package (MSIX) | `1.0.1.0` | `build_msix.ps1` reads pubspec; the Store requires the 4th part to be 0 |
| Android | versionName `1.0.1`, versionCode `2` | Flutter's default (`flutter.versionName` / `flutter.versionCode`) |
| Laptop brain | `__version__ = "1.0.1"` in `software/laptop/spike_brain/__init__.py`, sent in its hello | edit by hand with pubspec (a Flutter test fails if they differ) |

## Which number to raise

- **PATCH** (1.0.0 -> 1.0.1): fixes only, nothing new for the user to learn.
- **MINOR** (1.0.x -> 1.1.0): something new that works with what people already have (a new trick, the
  on-device AI pack, a new setting).
- **MAJOR** (1.x -> 2.0.0): a change that breaks something people rely on: a new robot generation, a
  protocol change old robots or phones cannot follow, a redesign that moves everything.
- **BUILD** (`+N`): raise it for EVERY build that goes to a store, even when the version stays (Google Play
  refuses a versionCode it has seen). Never lower it.

## Rules

1. Every Microsoft Store submission needs a HIGHER package version than the last one it accepted (and than
   any package still in certification). A rejected submission's number can be reused.
2. After changing pubspec: `dart run tool/sync_brand.dart`, set the brain's `__version__`, run the tests.
3. The phone app and the laptop brain are released together with the same version; the protocol has its
   own version (software/protocol/PROTOCOL.md) and is what decides whether two sides can talk.
4. Tag the release in git as `v1.0.0` when it is submitted.
